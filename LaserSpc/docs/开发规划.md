# LaserSpc 当前阶段开发规划

## 1. 方案分析结论

根据 `/root/qt-program/方案输出` 下的规划、周计划、架构说明和设计模式说明，`LaserSpc` 当前阶段必须按 `SPC 查询看板 MVP` 落地，而不是按完整镭雕上位机系统建设。

当前阶段明确结论如下：

1. 目标范围是 `查询 + 统计 + 明细显示 + 轻量导出 + 基础集成`。
2. 首批页面固定为：
   - 数据总览
   - 不良统计
   - 单板记录
   - 点位记录
3. 暂不进入：
   - 设备接入
   - 实时采集
   - MES
   - 自动清理
   - 完整权限系统
   - 复杂报表中心
4. 技术基线采用：
   - `C++17`
   - `Qt 5.15.2`
   - `Qt Widgets`
   - `CMake`

## 2. 当前代码落地策略

第 1 周先完成稳定的可扩展骨架，不在页面里直接写 SQL，不让 UI 直接耦合数据源。当前工程采用以下分层：

1. `ui`
   - 主窗口、导航、公共筛选栏、页面空壳
2. `app`
   - `AppServiceFacade`，统一承接 UI 请求
3. `domain`
   - 查询对象、分页、排序、页面数据模型、仓储接口
4. `infrastructure`
   - 配置服务、日志、仓储实现

## 4. 当前实现范围

当前版本已经按方案搭建以下能力：

1. `MainWindow` 主壳层
2. 左侧导航和页面切换
3. 公共筛选栏
4. 四个业务页基础展示
5. `AppServiceFacade` 统一查询入口
6. `ISpcQueryRepository` 仓储抽象
7. `MockSpcRepository` 假数据链路
8. 基础配置服务

## 5. 后续在 LaserSpc 内继续推进的开发顺序

1. 第一步：把 `MockSpcRepository` 替换为真实数据库仓储
2. 第二步：实现总览页真实查询、分页、排序和导出
3. 第三步：实现不良统计页图表联动
4. 第四步：实现单板记录页和点位记录页的真实查询
5. 第五步：补充导出、异常处理、配置持久化和测试

## 6. 约束

后续所有实现都应继续遵守以下规则：

1. 所有工作默认在 `/root/qt-program/LaserSpc` 下进行。
2. UI 层不直接访问数据库。
3. 新需求若超出 MVP，需要先确认是否会破坏当前排期。
4. 优先保持目录边界和接口稳定，避免第 2 周后反复改壳层。
